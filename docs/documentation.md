# HTML documentation workflow

The HTML review area is a static site generated from repository Markdown, the
decision records and the checked-in Lynx evidence snapshot. Source material lives
in `docs/`; presentation templates and assets live in `docs/site/`. There are no
CDN assets, analytics, accounts or external runtime dependencies. Navigation and
reading work without JavaScript; search and architecture inspection use local JS.

## Open the review area

From the repository root:

```sh
nix --extra-experimental-features 'nix-command flakes' run .#docs
```

Open <http://127.0.0.1:8787>. The server binds to loopback. To use another port:

```sh
nix --extra-experimental-features 'nix-command flakes' run .#docs -- --port 8788
```

The server presents an immutable Nix build snapshot. After editing sources,
stop it with Ctrl-C and rerun the command to review a fresh build. This is not a
live-reload server or a background monitoring service.

## Build and review without a server

```sh
nix --extra-experimental-features 'nix-command flakes' build .#docs -o build/docs -L
```

Open `build/docs/index.html` in a browser or copy the complete output directory
to another machine. Relative links, styles and the bundled search index work
offline, including from `file://`. Every page has its raw Markdown source, and
linked implementation files/evidence are bundled when referenced by the docs.

For a writable build while editing:

```sh
nix --extra-experimental-features 'nix-command flakes' develop
python scripts/build-docs.py . build/docs-preview
python -m http.server 8788 --bind 127.0.0.1 --directory build/docs-preview
```

## Keep it accurate as we work

1. Update [project status](project-status.md) and the relevant
   [roadmap gate](roadmap.md) when evidence changes a workstream's status.
2. Update [tradeoffs](tradeoffs.md) with alternatives, consequences and the
   specific measurement or user choice needed to settle an item.
3. Record changed accepted choices in a new ADR. Supersede and link the old record;
   retain its original assumptions and calculations as history.
4. Put measurements and their scope in research/evidence. A core-only route result
   must not become full-board timing signoff; a passed simulation must not become
   a physical test claim.
5. Rebuild the site and run the documentation checks. Do not hand-edit generated
   HTML. Refresh procurement facts before ordering; historical prices and stock
   in research are dated observations.

The home page's resource bars are generated from the existing audit JSON rather
than retyped. The decision list reads the ADR status metadata. All repository
Markdown documents in the documented areas are included in the library and the
full-text search index. The curated navigation is configured in
`docs/site/navigation.json`.
Its `audit_evidence` field selects the current dated snapshot for the first
page's figures. When a new probe is accepted, add a new snapshot and advance that field;
retain prior snapshots and label historical tables with their measurement date.
The `integration_evidence` field selects the current portable-system proof. The
site checker verifies its code/tool-pin and media hashes against this checkout.
After changing an included source, run the affected checks and update the dated
snapshot from the resulting artifacts; retain historical snapshots as history.
The `design_evidence` list adds current component-level proofs, such as TMDS
encoding and reset control. The checker also validates those source hashes;
these proofs retain their own scope and do not replace the portable-system or
core-only evidence.

Every file in `docs/research/evidence` must be listed either as current or under
`historical_evidence`; the checker fails on an unclassified snapshot. After the
full `nix flake check` passes on a changed tree, run
`python scripts/refresh-evidence.py` to re-record the hashes of current
snapshots (`--check` only reports). It never edits historical snapshots, and it
does not regenerate recorded measurements: update those from the check outputs.

The work-gate strip on the roadmap page is generated from the roadmap itself.
Each numbered gate carries a `Gate: label · Done|Active|Pending` line directly
under its heading, and the site build fails if one is missing or malformed.

Build definitions are in [flake.nix](../flake.nix) and the
[Nix documentation recipe](../nix/docs.nix). The
[HTML generator](../scripts/build-docs.py) and
[site checker](../scripts/check-docsite.py) are project code.

The [chip design handbook](chip-design/overview.md) has original SVG diagrams
generated by [chip_diagrams.py](../scripts/chip_diagrams.py). Each block's SVG
label and the block description under the figure share one definition. The figures support keyboard
inspection, zoom, scrolling and standalone SVG export without an internet
connection. They document logical boundaries and implementation status; they
are not physical layouts or additional verification evidence.

## Validate

```sh
nix --extra-experimental-features 'nix-command flakes' build .#docs-check -L
nix --extra-experimental-features 'nix-command flakes' flake check -L
```

The site check verifies generated HTML links, local assets, heading targets,
decision records, search coverage and evidence-derived metrics. These checks
validate documentation structure; project status still requires an honest human
review of the underlying evidence.
